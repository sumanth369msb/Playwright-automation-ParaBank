## Section 1: Java Core & Advanced Theory

### 1.1 Core Syntax & Foundations

#### Q1: What is the fundamental difference between Primitive Types and Reference Types in Java?
* **Simple Explanation**: 
  - **Primitives** (`int`, `boolean`, `char`, `double`, etc.) hold their raw values directly. They live on the **Stack** memory (when declared as local variables) and have a fixed size (e.g., `int` is 4 bytes).
  - **Reference Types** (`String`, `Object`, `List`, custom classes) hold a **memory address (pointer)** that points to an object stored in the **Heap**.
* **Interview Punchline**: *"Primitives store values directly on the stack for fast access; reference variables store memory addresses pointing to objects on the heap."*

---

#### Q2: What is the exact difference between `==` and `.equals()`? Why must `hashCode()` be overridden whenever `equals()` is overridden?
* **Simple Explanation**:
  - `==` compares **memory references** (are both variables pointing to the exact same memory address?).
  - `.equals()` compares **logical state / values** (do both objects contain the same data?).
* **The `equals()` and `hashCode()` Contract**:
  - If two objects are equal according to `equals()`, they **MUST** return the exact same `hashCode()`.
  - If `hashCode()` is not overridden, two logically identical objects will get two different hash codes generated by `Object.hashCode()` (based on memory addresses).
* **What breaks if you don't override `hashCode()`?**
  - In hash-based collections (`HashMap`, `HashSet`), objects are placed into buckets based on their hash code. If you insert an object and later search with an equal object that has a different hash code, the lookup will inspect the wrong bucket and return `null`!
* **Code Example**:
```java
public class Employee {
    private final int id;
    private final String name;

    public Employee(int id, String name) {
        this.id = id;
        this.name = name;
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        Employee employee = (Employee) o;
        return id == employee.id && Objects.equals(name, employee.name);
    }

    @Override
    public int hashCode() {
        return Objects.hash(id, name);
    }
}
```

#### Q3: Why is `String` immutable in Java? Contrast `String`, `StringBuilder`, and `StringBuffer`.
* **Why Immutability?**
  1. **String Constant Pool (SCP)**: Multiple variables can reference the same string literal in heap memory (`"apple"`), saving massive memory.
  2. **Thread Safety**: Immutable strings can be shared across multiple threads without synchronization.
  3. **Security**: Sensitive parameters like database URLs, usernames, network sockets cannot be altered once instantiated.
  4. **HashCode Caching**: The hash code is calculated once at creation and cached, making hash table lookups extremely fast.
* **Comparison Matrix**:

| Feature | `String` | `StringBuilder` | `StringBuffer` |
| :--- | :--- | :--- | :--- |
| **Mutability** | Immutable | Mutable | Mutable |
| **Thread Safety** | Safe (read-only) | Unsafe (no synchronization) | Safe (`synchronized` methods) |
| **Performance** | Slow for concatenation | Fastest | Slower due to lock overhead |
| **Use Case** | Constants, keys, DTOs | String concatenation in a single thread | Legacy multi-threaded concatenation |

---

#### Q4: Is Java "Pass-by-Value" or "Pass-by-Reference"?
* **Simple Explanation**: **Java is strictly 100% Pass-by-Value.**
* **The Nuance**:
  - For primitive types, the actual value (e.g., number `5`) is copied into the method parameter.
  - For objects, the **reference (memory address)** is copied by value.
  - You can modify the internal state of the object via that copied reference, but if you reassign the reference variable inside the method (`param = new Object()`), the caller's reference remains unchanged!

### 1.2 JVM Internals & Memory Architecture

```
+------------------------------------------------------------------+
|                     JVM Run-Time Data Areas                      |
+------------------------------------------------------------------+
|      Shared across all threads       |    Per-thread private     |
| +----------------------------------+ | +-----------------------+ |
| |              HEAP                | | |      JVM STACK        | |
| |  [Young Gen (Eden, S0, S1)]     | | |  (Stack frames,       | |
| |  [Old / Tenured Generation]      | | |   local variables,    | |
| +----------------------------------+ | |   operand stack)      | |
| |           METASPACE              | | +-----------------------+ |
| |  (Class metadata, Method info,   | | |      PC REGISTER      | |
| |   Static variables - Native Mem) | | +-----------------------+ |
| +----------------------------------+ | |  NATIVE METHOD STACK  | |
+------------------------------------------------------------------+
```

#### Q5: Explain the JVM Memory Model (Stack vs. Heap vs. Metaspace).
* **1. JVM Stack**:
  - Thread-private. Created when a thread starts.
  - Stores **Stack Frames**. Each method call pushes a frame containing local variables, primitive values, and object reference pointers.
  - Fast allocation; automatically cleared when the method exits.
  - Error: `StackOverflowError` (e.g., infinite recursion).
* **2. Heap Memory**:
  - Shared across all threads.
  - Stores all **Objects** and JRE arrays created via `new`.
  - Managed exclusively by the **Garbage Collector (GC)**.
  - Error: `OutOfMemoryError: Java heap space`.
* **3. Metaspace (Java 8+)**:
  - Replaced PermGen. Allocated out of **Native OS Memory** (off-heap).
  - Stores class definitions, method bytecode, annotations, and constant pools.
  - Automatically resizes up to available system memory (unless constrained by `-XX:MaxMetaspaceSize`).

---

#### Q6: How does Garbage Collection work? Explain the Generational Hypothesis and modern collectors (G1 vs. ZGC).
* **The Weak Generational Hypothesis**:
  - Most allocated objects have very short lifespans (over 90% die shortly after creation).
  - Dividing memory into generations allows GC to focus only on regions where dead objects are concentrated.
* **Heap Partitioning**:
  - **Young Generation**:
    - **Eden**: Where new objects are initially allocated.
    - **Survivor Spaces (S0 & S1)**: Objects surviving minor GC are moved here and aged (tenured).
  - **Old Generation (Tenured)**: Objects that survive multiple GC cycles (default threshold: 15) are promoted here.
* **Modern Collectors Comparison**:
  1. **G1 GC (Garbage-First)**:
     - Default since Java 9.
     - Divides heap into equal-sized virtual regions (~1MB to 32MB).
     - Tracks region garbage density and collects regions with the most garbage first to meet user-defined pause time targets (`-XX:MaxGCPauseMillis`).
  2. **ZGC (Z Garbage Collector - Production in Java 15+)**:
     - Ultra-low latency collector designed for massive heaps (terabytes).
     - Performs all expensive work (mark, compact, relocate) **concurrently** with application threads using colored pointers and load barriers.
     - Guarantees pause times under **1 millisecond**.

### 1.3 Multithreading & Concurrency Engineering

#### Q7: Explain the Thread Lifecycle in Java.
A thread transitions through 6 states (`java.lang.Thread.State`):
1. **NEW**: Created (`new Thread()`), but `start()` has not been called.
2. **RUNNABLE**: Executing in JVM or waiting for OS CPU scheduling.
3. **BLOCKED**: Waiting to acquire a monitor lock to enter/re-enter a `synchronized` block.
4. **WAITING**: Waiting indefinitely for another thread to take action (`Object.wait()`, `Thread.join()`, `LockSupport.park()`).
5. **TIMED_WAITING**: Waiting for a specified time (`Thread.sleep(ms)`, `wait(ms)`).
6. **TERMINATED**: Completed execution or terminated by an unhandled exception.

---

#### Q8: What is the difference between `synchronized`, `volatile`, and `AtomicInteger`?
* **`volatile`**:
  - Guarantees **Visibility** (forces reads/writes directly to main memory, bypassing CPU caches).
  - Prevents compiler instruction reordering (happens-before relationship).
  - **Does NOT guarantee atomicity** (e.g., `count++` is 3 operations: read, increment, write; volatile will cause race conditions).
* **`synchronized`**:
  - Guarantees **both Visibility and Atomicity**.
  - Acquires an exclusive monitor lock on the object. Only one thread can execute the block at a time; others block.
* **`AtomicInteger` (Lock-Free Concurrency)**:
  - Uses hardware-level **Compare-And-Swap (CAS)** CPU instructions.
  - Completely non-blocking (threads do not sleep or context-switch). Extremely high throughput under moderate contention.

---

#### Q9: What is `ConcurrentHashMap` and how does it achieve high throughput compared to `Collections.synchronizedMap()`?
* **`Collections.synchronizedMap()`**:
  - Wraps a HashMap with a single global object lock. Every single read and write serializes behind this single lock. Catastrophic bottleneck under high concurrency.
* **`ConcurrentHashMap` (Java 8+)**:
  - **Reads are 100% lock-free**: `get()` operations access `volatile` node values without acquiring locks.
  - **Fine-grained Bucket-Level Locking**: Writes lock **only the specific head node of the bucket bin** (`synchronized(node)`) where the hash collision lands.
  - **Lock-Free Inserts**: If the bucket is empty, it inserts the new node using atomic **CAS** without any lock!
  - **Concurrent Rehashing**: Supports multi-threaded parallel resizing.

#### Q10: How do you prevent Deadlocks? What are the Coffman Conditions?
* A deadlock occurs when two or more threads are blocked forever, each waiting for a lock held by the other.
* **The 4 Coffman Conditions required for a deadlock**:
  1. *Mutual Exclusion*: Resources cannot be shared.
  2. *Hold and Wait*: A thread holds one resource while waiting for another.
  3. *No Preemption*: Resources cannot be forcibly taken away.
  4. *Circular Wait*: Thread A waits for B, B waits for A.
* **Prevention Strategies**:
  - **Lock Ordering**: Always acquire shared locks in the exact same global order across all threads.
  - **Timed Locks**: Use `ReentrantLock.tryLock(timeout, unit)` instead of `synchronized` so threads release acquired locks if they cannot acquire the next lock within a SLA.

#### Q11: What is `ThreadLocal`? Why is it indispensable in parallel test automation frameworks, and how do you prevent memory leaks?
* **Simple Explanation**:
  - `ThreadLocal` provides thread-scoped variables. Each thread accessing a `ThreadLocal` has its own independently initialized, completely isolated copy of the variable.
* **The SDET Problem It Solves**:
  - When running test suites in parallel (e.g., TestNG `parallel="methods"` with 4–8 worker threads), sharing a static `WebDriver` or `ExtentTest` instance causes race conditions. Thread A clicks a button while Thread B navigates to a new URL, leading to test collisions and `StaleElementReferenceException`.
  - Wrapping the driver in `ThreadLocal<WebDriver>` guarantees that each thread manipulates its own browser session with zero interference.
* **The Critical Memory Leak Trap**:
  - Thread pools (like those in test runners or CI/CD workers) **reuse** threads rather than destroying them.
  - `ThreadLocal` stores data in an internal `ThreadLocalMap` where keys are weak references, but values are strong references. If you do not explicitly call `.remove()`, the object remains pinned in memory forever, eventually triggering an `OutOfMemoryError: Java heap space`.
  - **Golden Rule**: Always call `.remove()` in `@AfterMethod` / `@AfterEach`.
* **Production SDET Pattern**:
```java
public class DriverManager {
    private static final ThreadLocal<WebDriver> driverThreadLocal = new ThreadLocal<>();

    private DriverManager() {} // Prevent direct instantiation

    public static WebDriver getDriver() {
        return driverThreadLocal.get();
    }

    public static void setDriver(WebDriver driver) {
        driverThreadLocal.set(driver);
    }

    public static void quitDriver() {
        if (driverThreadLocal.get() != null) {
            driverThreadLocal.get().quit();
            driverThreadLocal.remove(); // CRITICAL: prevents thread pool memory leak!
        }
    }
}
```

#### Q12: Explain `ExecutorService` and Java Thread Pools. What is the difference between `submit()` vs. `execute()`, and `Callable` vs. `Runnable`?
* **Simple Explanation**:
  - Instead of spawning costly OS threads manually for every test task (`new Thread()`), an `ExecutorService` maintains a reusable pool of pre-warmed worker threads to execute tasks concurrently.
* **Core Differences**:

| Feature | `Runnable` | `Callable<V>` |
| :--- | :--- | :--- |
| **Return Value** | `void` (no result) | Returns generic value `V` |
| **Exception Handling** | Cannot throw checked exceptions | Can throw checked `Exception` |
| **Method** | `run()` | `call()` |

| Method | `execute(Runnable)` | `submit(Callable / Runnable)` |
| :--- | :--- | :--- |
| **Interface** | `Executor` | `ExecutorService` |
| **Return** | `void` (Fire and forget) | Returns `Future<T>` |
| **Error Handling** | Uncaught exceptions bubble to Thread uncaught handler | Exceptions are captured and rethrown when calling `Future.get()` |

* **SDET Practical Application (Parallel API Health Checks)**:
```java
ExecutorService pool = Executors.newFixedThreadPool(3);

Callable<Integer> checkAuth = () -> ApiClient.getStatusCode("/auth/status");
Callable<Integer> checkDb = () -> ApiClient.getStatusCode("/db/health");

Future<Integer> authResult = pool.submit(checkAuth);
Future<Integer> dbResult = pool.submit(checkDb);

// Blocks until completed or timeout occurs
System.out.println("Auth Service Status: " + authResult.get(5, TimeUnit.SECONDS));
System.out.println("DB Service Status: " + dbResult.get(5, TimeUnit.SECONDS));

pool.shutdown();
```

### 1.4 Collections Framework In-Depth

#### Q13: Deep Dive: How does `HashMap` work internally in Java 8+?
1. **Underlying Data Structure**:
   - An array of buckets: `Node<K,V>[] table`.
2. **Hash Function & Index Calculation**:
   - Computes hash using bit-shifting to distribute higher bits into lower bits:
     ```java
     static final int hash(Object key) {
         int h;
         return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
     }
     ```
   - Target bucket index is calculated using bitwise AND: `index = (n - 1) & hash` (equivalent to modulo `hash % n`, but much faster).
3. **Collision Handling**:
   - Multiple keys with the same index form a Singly Linked List in that bucket.
4. **Treeification Threshold**:
   - When a bucket list length reaches **8** and the total table capacity is at least **64**, the LinkedList transforms into a **Red-Black Balanced Binary Search Tree**.
   - Lookup complexity drops from $O(N)$ worst-case to **$O(\log N)$**.
   - If elements drop to **6** during resizing, it untreeifies back to a LinkedList.
5. **Load Factor & Resizing**:
   - Default initial capacity = 16. Default load factor = 0.75.
   - When elements exceed $16 \times 0.75 = 12$, the table doubles to 32 buckets, and all nodes are rehashed/reindexed.

#### Q14: Compare `ArrayList` vs. `LinkedList`. When would you choose one over the other?
* **`ArrayList`**:
   - Backed by a dynamic array.
   - **Random access**: $O(1)$ via index.
   - **Cache locality**: Elements occupy contiguous memory; CPU prefetching makes iteration blazing fast.
   - Resizing requires allocating a new array (1.5x) and copying elements via `System.arraycopy`.
* **`LinkedList`**:
   - Backed by doubly linked nodes (`prev`, `data`, `next`).
   - **Random access**: $O(N)$ (must traverse from head or tail).
   - **Insert/Delete at ends**: $O(1)$.
   - High memory overhead due to pointer objects per node; poor cache locality.
* **Verdict**: Always default to `ArrayList` unless you are implementing a Queue/Deque where insertions and deletions strictly happen at the ends.

---

#### Q15: Compare `Set` implementations (`HashSet` vs. `LinkedHashSet` vs. `TreeSet`). How does `HashSet` enforce uniqueness internally?
* **Simple Explanation**:
  - `HashSet`: Unordered collection of unique items. Backed internally by a `HashMap`. Time complexity: $O(1)$ add/contains/remove.
  - `LinkedHashSet`: Maintains **insertion order** using a doubly linked list running through all buckets. Time complexity: $O(1)$.
  - `TreeSet`: Maintains **sorted natural order** (or custom `Comparator`). Backed by a `TreeMap` (Red-Black tree). Time complexity: $O(\log N)$.
* **How `HashSet` Enforces Uniqueness**:
  - Whenever you call `hashSet.add(element)`, `HashSet` calls `map.put(element, PRESENT)` under the hood, where `PRESENT` is a dummy `static final Object`.
  - `HashMap.put()` checks the bucket for existing keys using `hashCode()` and `equals()`.
  - If the key is already present, `map.put()` returns the old dummy value; `hashSet.add()` sees it was already there and returns `false`.
* **Comparison Matrix**:

| Feature | `HashSet` | `LinkedHashSet` | `TreeSet` |
| :--- | :--- | :--- | :--- |
| **Ordering** | None (Random) | Insertion order | Sorted order (Natural/Comparator) |
| **Internal Engine**| `HashMap` | `LinkedHashMap` | `TreeMap` (Red-Black Tree) |
| **Lookup / Add** | $O(1)$ | $O(1)$ | $O(\log N)$ |
| **Null Allowed?** | Yes (1 null element) | Yes (1 null element) | No (throws `NullPointerException`) |

#### Q16: What is the exact difference between `Comparable` and `Comparator`? When do you choose each?
* **Simple Explanation**:
  - **`Comparable`**: Used for **natural ordering** defined inside the class itself. Modifies the class. Implements `compareTo(T o)`. (Package: `java.lang`).
  - **`Comparator`**: Used for **multiple custom sorting criteria** defined outside the class. Does not modify the class. Implements `compare(T o1, T o2)`. (Package: `java.util`).
* **Interview Punchline**: *"Use `Comparable` when a domain model has a single natural sort order (e.g., Employee ID); use `Comparator` when you need flexible, multiple sort orders (e.g., sort products by price, then by rating, then by name) without modifying the original class."*
* **Real-World SDET Code (Sorting Test Results / API Responses)**:
```java
public class TestCaseResult {
    private final String name;
    private final long executionTimeMs;

    public TestCaseResult(String name, long executionTimeMs) {
        this.name = name;
        this.executionTimeMs = executionTimeMs;
    }

    public String getName() { return name; }
    public long getExecutionTimeMs() { return executionTimeMs; }
}

// Modern Java 8+ Comparator with Method References:
List<TestCaseResult> results = getTestResults();

// Sort by execution time descending, then alphabetically by test name:
results.sort(
    Comparator.comparingLong(TestCaseResult::getExecutionTimeMs).reversed()
              .thenComparing(TestCaseResult::getName)
);
```

### 1.5 Java 8 Functional Programming & Streams API

#### Q17: Explain Functional Interfaces (`Predicate`, `Function`, `Consumer`, `Supplier`) and Lambda Expressions.
* **What is a Functional Interface?**
  - An interface that contains **exactly one abstract method** (SAM - Single Abstract Method). Annotated with `@FunctionalInterface`.
  - Lambdas provide inline, anonymous implementations of that single abstract method.
* **The 4 Core Functional Interfaces**:

| Interface | Signature | Return Type | Typical Test Automation Use Case |
| :--- | :--- | :--- | :--- |
| **`Predicate<T>`** | `boolean test(T t)` | `boolean` | Filtering test data (e.g., `user -> user.isActive()`) |
| **`Function<T, R>`**| `R apply(T t)` | `R` (Transform) | Converting API responses (e.g., `account -> account.getId()`) |
| **`Consumer<T>`** | `void accept(T t)` | `void` (Side effect) | Executing actions (e.g., `driver -> driver.close()`, logging) |
| **`Supplier<T>`** | `T get()` | `T` (Factory) | Lazy evaluation, generating random test payloads |

* **Code Example**:
```java
// Predicate: Evaluate test condition
Predicate<Integer> isSuccessCode = code -> code >= 200 && code < 300;
System.out.println(isSuccessCode.test(201)); // true

// Supplier: Lazy test payload generation
Supplier<String> tokenGenerator = () -> "Bearer " + UUID.randomUUID();
String authHeader = tokenGenerator.get();
```

#### Q18: Explain the Java 8 Streams API (Intermediate vs. Terminal Operations). How do you apply Streams in test automation?
* **Core Concepts**:
  - A `Stream` is a pipeline of computations applied to a collection of data. It does not store elements; it operates on the source data lazily.
  - **Intermediate Operations** (Lazy): Return a new `Stream`. They do not execute until a terminal operation is called (e.g., `filter()`, `map()`, `sorted()`, `distinct()`, `limit()`).
  - **Terminal Operations** (Eager): Trigger pipeline execution and produce a result or side-effect (e.g., `collect()`, `forEach()`, `count()`, `anyMatch()`, `findFirst()`).
* **Real-World SDET Code (Validating REST API Account Payloads)**:
```java
List<Account> accounts = fetchAccountsFromApi();

// Task: Find all CHECKING accounts with balance > $1000 and extract their IDs
List<Integer> highValueCheckingAccountIds = accounts.stream()
    .filter(acc -> "CHECKING".equalsIgnoreCase(acc.getType()))
    .filter(acc -> acc.getBalance() > 1000.0)
    .map(Account::getId)
    .collect(Collectors.toList());

// Task: Assert whether any account is overdrawn
boolean hasOverdrawnAccount = accounts.stream()
    .anyMatch(acc -> acc.getBalance() < 0.0);
```

#### Q19: Explain Records and Sealed Classes introduced in Java 17.
* **Records (`record`)**:
  - Purpose: Eliminates boilerplate for immutable data carrier classes (DTOs, test fixtures, API responses).
  - Automatically generates `private final` fields, canonical constructor, getters (`id()`, `name()`), `equals()`, `hashCode()`, and `toString()`.
  ```java
  public record UserPayload(int id, String email, String role) {}
  // Usage:
  UserPayload user = new UserPayload(1, "sdet@apple.com", "ADMIN");
  System.out.println(user.email()); // Note: getters do not have "get" prefix
  ```
* **Sealed Classes (`sealed`, `permits`)**:
  - Allows a class/interface to explicitly control and restrict which subclasses are allowed to extend or implement it.
  ```java
  public sealed interface DriverFactory permits ChromeDriver, FirefoxDriver, SafariDriver {}
  public final class ChromeDriver implements DriverFactory {}
  public final class FirefoxDriver implements DriverFactory {}
  public final class SafariDriver implements DriverFactory {}
  ```

#### Q20: What are Virtual Threads in Java 21 (Project Loom)? How do they revolutionize high-scale test runners and microservices?
* **Platform Threads (Legacy)**:
  - 1:1 mapping with OS kernel threads. Heavyweight (~1MB memory per stack).
  - Context switching requires OS kernel transitions. Creating 5,000 threads can exhaust server memory.
* **Virtual Threads (Java 21)**:
  - Lightweight, user-mode threads managed entirely by the **JVM**, not the OS.
  - Millions of virtual threads can run concurrently (~few hundred bytes of initial memory).
  - **The Magic of Blocking I/O**: When a virtual thread performs blocking I/O (e.g., waiting for an HTTP API response or DB query), the JVM unmounts the virtual thread from its underlying carrier OS thread. The carrier thread immediately executes other tasks. When I/O completes, the JVM re-mounts the virtual thread seamlessly!
  - **Impact on SDET**: Massive scale parallel test execution without complex reactive programming or thread pool limits.

## Section 2: Object-Oriented Programming (OOP)

### 2.1 The Four Pillars (Theory & Real-World SDET Scenarios)

#### 1. Encapsulation
* **Definition**: Bundling data (state) and methods (behavior) within a single unit while restricting direct outside access to internal fields using access modifiers (`private`).
* **Real-World SDET Architecture**:
  - In automation frameworks, direct access to the `WebDriver` or `APIRequestContext` is encapsulated inside a base manager. Tests interact only through controlled actions, preventing corrupted state.
```java
// Encapsulated Page Object
public class LoginPage {
    private final WebDriver driver;
    private final By usernameField = By.id("user");
    private final By passwordField = By.id("pass");
    private final By submitBtn = By.id("submit");

    public LoginPage(WebDriver driver) {
        this.driver = driver;
    }

    public void login(String username, String password) {
        driver.findElement(usernameField).sendKeys(username);
        driver.findElement(passwordField).sendKeys(password);
        driver.findElement(submitBtn).click();
    }
}
```

---

#### 2. Inheritance
* **Definition**: A mechanism where a child class acquires the properties and methods of a parent class using the `extends` keyword, facilitating code reuse.
* **Real-World SDET Architecture**:

### 2.2 Interfaces vs. Abstract Classes in Framework Design

| Feature | Interface | Abstract Class |
| :--- | :--- | :--- |

| **Framework Role** | Defines **contracts** (e.g., `TestReporter`, `DriverProvider`) | Provides **base skeleton & shared state** (e.g., `BasePage`) |

### 2.4 Critical Keywords: `super`, `this`, `final`, `static`

1. **`super`**:
   - `super()` invokes the parent class constructor (must be the first line in the child constructor).
   - `super.methodName()` calls an overridden method in the superclass.
2. **`this`**:
   - Refers to the current class instance.
   - `this(args)` chains constructors within the same class.
   - Eliminates shadowing: `this.name = name`.
3. **`final`**:
   - Variable $\rightarrow$ Value cannot be reassigned (constant).
   - Method $\rightarrow$ Cannot be overridden by subclasses.
   - Class $\rightarrow$ Cannot be extended (e.g., `java.lang.String`).
4. **`static`**:
   - Belongs to the **Class**, not individual object instances.
   - Shared across all instances in the JVM memory.
   - Static methods cannot access non-static instance fields directly.

### 2.5 Essential Design Patterns in Test Automation

#### 1. The Factory Pattern (Decoupled Driver Instantiation)
* **Definition**: A creational pattern that provides an interface for creating objects in a superclass, but allows subclasses or factory methods to alter the type of objects that will be created.
* **Why SDETs Use It**:
  - Tests should never instantiate concrete browsers like `new ChromeDriver()` directly. If Chrome switches to headless or options change, modifying 500 test classes violates the **Open-Closed Principle (OCP)**.
  - A `DriverFactory` encapsulates instantiation logic in one place.
* **Code Example**:
```java
public class DriverFactory {
    public static WebDriver createDriver(String browser) {
        return switch (browser.toUpperCase()) {
            case "CHROME" -> {
                ChromeOptions options = new ChromeOptions();
                options.addArguments("--headless=new", "--disable-gpu", "--no-sandbox");
                yield new ChromeDriver(options);
            }
            case "FIREFOX" -> new FirefoxDriver(new FirefoxOptions());
            case "SAFARI"  -> new SafariDriver();
            default -> throw new IllegalArgumentException("Unsupported browser: " + browser);
        };
    }
}
```

---

#### 2. The Thread-Safe Singleton Pattern (Double-Checked Locking)
* **Definition**: Ensures that a class has only one instance and provides a global point of access to it.
* **When to Use in SDET**:
  - For reading global configuration files (`config.properties`, environment URLs, database connection pools) where loading from disk multiple times creates unnecessary I/O overhead.
* **Double-Checked Locking Implementation**:
```java
public class ConfigManager {
    // volatile ensures immediate visibility across threads and prevents instruction reordering
    private static volatile ConfigManager instance;
    private final Properties properties;

    private ConfigManager() {
        properties = new Properties();
        try (InputStream input = getClass().getClassLoader().getResourceAsStream("config.properties")) {
            properties.load(input);
        } catch (IOException e) {
            throw new RuntimeException("Failed to load framework configuration", e);
        }
    }

    public static ConfigManager getInstance() {
        if (instance == null) {                         // 1st Check (No locking overhead once initialized)
            synchronized (ConfigManager.class) {
                if (instance == null) {                 // 2nd Check (Guarantees only one thread instantiates)
                    instance = new ConfigManager();
                }
            }
        }
        return instance;
    }

    public String getProperty(String key) {
        return properties.getProperty(key);
    }
}
```

#### 3. The #1 SDET Interview Gotcha: *"Can We Make `WebDriver` a Singleton?"*
* **The Trap Question**: *"To save memory, why don't we design our `WebDriver` as a Singleton so only one instance is shared across the entire framework?"*
* **The Correct Answer**:
  - **"No. Never make `WebDriver` a Singleton in modern test automation."**
  - **The Reason**: A Singleton guarantees exactly **one** object per JVM. If you run test suites in parallel across multiple worker threads, every thread will battle to control that single browser window. Test A clicks while Test B navigates, causing immediate race conditions and test failures.
  - **The Industry Standard**: Combine the **Factory Pattern** (to instantiate the driver) with **`ThreadLocal<WebDriver>`** (to give each parallel worker thread its own isolated driver instance).

## Section 3: Data Structures & Algorithms (DSA)

### 3.1 Big O Complexity Analysis

```
Time Complexity Growth Order:
O(1) < O(log N) < O(N) < O(N log N) < O(N^2) < O(2^N) < O(N!)
```

* **$O(1)$ - Constant Time**: Hash map lookup, array index access.
* **$O(\log N)$ - Logarithmic Time**: Binary Search, Balanced BST lookup. Divides problem size in half each step.
* **$O(N)$ - Linear Time**: Traversing an array or LinkedList once.
* **$O(N \log N)$ - Linearithmic Time**: Optimal comparison sorting (MergeSort, HeapSort, QuickSort average).
* **$O(N^2)$ - Quadratic Time**: Nested loops over array elements (Bubble sort, brute force pairs).
* **$O(2^N)$ - Exponential Time**: Recursive calculation of subsets, traveling salesperson.

---

### 3.2 Linear Data Structures

#### 1. Arrays & Dynamic Arrays
* Contiguous memory storage. 
* Instant element access: $\text{Memory Address} = \text{Base Address} + (\text{Index} \times \text{Element Size})$.
* Lookup: $O(1)$. Insert/Delete at arbitrary position: $O(N)$ (requires shifting elements).

#### 2. Linked Lists (Singly & Doubly)
* Nodes connected by pointers. Dynamic size, non-contiguous memory.
* Insertion/Deletion at known pointer: $O(1)$.
* Search/Access: $O(N)$.
* Fast & Slow Pointer (Floyd's Cycle-Finding Algorithm):
  - Slow moves 1 step; Fast moves 2 steps. If they meet, a cycle exists!

#### 3. Stacks & Queues
* **Stack**: LIFO (Last-In-First-Out). Operations: `push`, `pop`, `peek` ($O(1)$).
  - Use cases: Parentheses matching, undo buffers, DFS.
* **Queue**: FIFO (First-In-First-Out). Operations: `offer`, `poll`, `peek` ($O(1)$).
  - Use cases: BFS graph traversal, request buffering.
* **Deque**: Double-ended queue (`ArrayDeque`). Supports insertions and deletions at both ends in $O(1)$.

#### 4. Heaps / Priority Queues
* Complete Binary Tree satisfying the Heap Property:
  - **Min-Heap**: Parent value $\le$ child values. Root is always the minimum.
  - **Max-Heap**: Parent value $\ge$ child values. Root is always the maximum.
* Operations:
  - Insert (`offer`): $O(\log N)$
  - Extract Root (`poll`): $O(\log N)$
  - Peek Root: $O(1)$
* High-frequency interview use case: Top K Frequent Elements, Kth Largest Element, Task Scheduling.

---

### 3.3 Non-Linear Data Structures

#### 1. Binary Search Trees (BST)
* Binary tree where for every node:
  - All left subtree nodes $<$ current node.
  - All right subtree nodes $>$ current node.
* **Search, Insert, Delete**:
  - Balanced Tree (AVL, Red-Black): $O(\log N)$.
  - Degenerate (Skewed) Tree: $O(N)$ (behaves like a linked list).
* **Tree Traversals**:
  - **In-Order** (Left $\rightarrow$ Root $\rightarrow$ Right): Visits BST in strictly sorted ascending order.
  - **Pre-Order** (Root $\rightarrow$ Left $\rightarrow$ Right): Useful for tree serialization/cloning.
  - **Post-Order** (Left $\rightarrow$ Right $\rightarrow$ Root): Useful for bottom-up deletion and expression evaluation.
  - **Level-Order** (BFS): Breadth-first traversal layer by layer using a Queue.

#### 2. Graphs
* Consists of Vertices ($V$) and Edges ($E$).
* **Representation**:
  - *Adjacency List*: `Map<Integer, List<Integer>>` (Space efficient: $O(V + E)$).
  - *Adjacency Matrix*: `int[][]` (Fast edge lookup $O(1)$, but space $O(V^2)$).
* **Graph Algorithms**:
  - **BFS**: Uses a `Queue`. Finds the **shortest path** on unweighted graphs.
  - **DFS**: Uses Recursion or a `Stack`. Explores full paths; detects cycles and connected components.

---

### 3.4 Core Algorithmic Techniques

1. **Two Pointers**: Used on sorted arrays or linked lists to search pairs, reverse in-place, or partition data in $O(N)$ time with $O(1)$ space.
2. **Sliding Window**: Optimizes nested-loop subarray/substring problems from $O(N^2)$ to $O(N)$ by maintaining a dynamic window boundary (`left`, `right`).
3. **Binary Search**: Searches ordered search spaces by repeatedly testing the midpoint:
   ```java
   int low = 0, high = arr.length - 1;
   while (low <= high) {
       int mid = low + (high - low) / 2; // Prevents integer overflow
       if (arr[mid] == target) return mid;
       else if (arr[mid] < target) low = mid + 1;
       else high = mid - 1;
   }
   ```

### Problem 1: Two Sum
* **Description**: Given an array of integers `nums` and an integer `target`, return indices of the two numbers such that they add up to `target`.
* **30-Second Interview Explanation**: *"Instead of a brute-force $O(N^2)$ nested loop, use a HashMap to store each number and its index. For every number `x`, calculate its complement `target - x`. If the complement exists in the map, return the pair. Otherwise, insert `x` into the map."*
* **Complexity**: Time: $O(N)$ | Space: $O(N)$
* **Java Solution**:
```java
public class TwoSum {
    public static int[] twoSum(int[] nums, int target) {
        Map<Integer, Integer> map = new HashMap<>();
        for (int i = 0; i < nums.length; i++) {
            int complement = target - nums[i];
            if (map.containsKey(complement)) {
                return new int[] { map.get(complement), i };
            }
            map.put(nums[i], i);
        }
        throw new IllegalArgumentException("No two sum solution found");
    }
}
```

### Problem 2: Valid Parentheses
* **Description**: Given a string `s` containing `'(', ')', '{', '}', '[', ']'`, determine if the input string is valid.
* **30-Second Interview Explanation**: *"Use a Stack. Iterate through each character: when an opening bracket is seen, push its expected closing counterpart onto the stack. When a closing bracket appears, check if the stack is empty or if the popped element doesn't match. If the stack is empty at the end, the string is valid."*
* **Complexity**: Time: $O(N)$ | Space: $O(N)$
* **Java Solution**:
```java
public class ValidParentheses {
    public static boolean isValid(String s) {
        Deque<Character> stack = new ArrayDeque<>();
        for (char c : s.toCharArray()) {
            if (c == '(') stack.push(')');
            else if (c == '{') stack.push('}');
            else if (c == '[') stack.push(']');
            else if (stack.isEmpty() || stack.pop() != c) {
                return false;
            }
        }
        return stack.isEmpty();
    }
}
```

### Problem 3: Merge Two Sorted Lists
* **Description**: Merge two sorted linked lists and return it as a sorted list.
* **30-Second Interview Explanation**: *"Create a dummy node to act as the head of the merged list. Compare the heads of both lists: attach the smaller node to our tracking pointer and advance that list. Once one list is exhausted, attach the remaining tail directly."*
* **Complexity**: Time: $O(N + M)$ | Space: $O(1)$
* **Java Solution**:
```java
class ListNode {
    int val;
    ListNode next;
    ListNode(int val) { this.val = val; }
}

public class MergeSortedLists {
    public static ListNode mergeTwoLists(ListNode list1, ListNode list2) {
        ListNode dummy = new ListNode(-1);
        ListNode current = dummy;

        while (list1 != null && list2 != null) {
            if (list1.val <= list2.val) {
                current.next = list1;
                list1 = list1.next;
            } else {
                current.next = list2;
                list2 = list2.next;
            }
            current = current.next;
        }

        // Attach remaining elements
        current.next = (list1 != null) ? list1 : list2;
        return dummy.next;
    }
}
```

### Problem 4: Longest Substring Without Repeating Characters
* **Description**: Given a string `s`, find the length of the longest substring without duplicate characters.
* **30-Second Interview Explanation**: *"Use a dynamic Sliding Window with two pointers and a HashMap storing characters and their most recent index. When a duplicate character is encountered inside the active window, slide the left pointer past the previous occurrence."*
* **Complexity**: Time: $O(N)$ | Space: $O(\min(N, M))$ where $M$ is alphabet size
* **Java Solution**:
```java
public class LongestSubstring {
    public static int lengthOfLongestSubstring(String s) {
        Map<Character, Integer> lastSeen = new HashMap<>();
        int maxLength = 0;
        int left = 0;

        for (int right = 0; right < s.length(); right++) {
            char c = s.charAt(right);
            if (lastSeen.containsKey(c)) {
                // Move left pointer to right of previous occurrence (without moving backwards)
                left = Math.max(left, lastSeen.get(c) + 1);
            }
            lastSeen.put(c, right);
            maxLength = Math.max(maxLength, right - left + 1);
        }
        return maxLength;
    }
}
```

### Problem 5: Reverse a Linked List
* **Description**: Reverse a singly linked list in-place.
* **30-Second Interview Explanation**: *"Maintain three pointers: `prev`, `curr`, and `next`. In each iteration, save `curr.next`, redirect `curr.next` backwards to `prev`, and shift `prev` and `curr` forward by one node. Return `prev` as the new head."*
* **Complexity**: Time: $O(N)$ | Space: $O(1)$
* **Java Solution**:
```java
public class ReverseLinkedList {
    public static ListNode reverseList(ListNode head) {
        ListNode prev = null;
        ListNode curr = head;

        while (curr != null) {
            ListNode nextTemp = curr.next;
            curr.next = prev;
            prev = curr;
            curr = nextTemp;
        }
        return prev;
    }
}
```

### Problem 7: Binary Tree Level Order Traversal
* **Description**: Given the root of a binary tree, return the level order traversal of its nodes' values (BFS).
* **30-Second Interview Explanation**: *"Use a Queue to conduct a Breadth-First Search. In each loop iteration, capture the queue size representing all nodes on the current level. Poll that exact number of nodes, append their values to a level list, and add their non-null children to the queue."*
* **Complexity**: Time: $O(N)$ | Space: $O(N)$
* **Java Solution**:
```java
class TreeNode {
    int val;
    TreeNode left, right;
    TreeNode(int val) { this.val = val; }
}

public class LevelOrderTraversal {
    public static List<List<Integer>> levelOrder(TreeNode root) {
        List<List<Integer>> result = new ArrayList<>();
        if (root == null) return result;

        Queue<TreeNode> queue = new ArrayDeque<>();
        queue.offer(root);

        while (!queue.isEmpty()) {
            int levelSize = queue.size();
            List<Integer> currentLevel = new ArrayList<>();

            for (int i = 0; i < levelSize; i++) {
                TreeNode node = queue.poll();
                currentLevel.add(node.val);

                if (node.left != null) queue.offer(node.left);
                if (node.right != null) queue.offer(node.right);
            }
            result.add(currentLevel);
        }
        return result;
    }
}
```

### Problem 8: Kth Largest Element in an Array
* **Description**: Find the $k$-th largest element in an unsorted array.
* **30-Second Interview Explanation**: *"Maintain a Min-Heap of fixed capacity $k$. As we iterate through the array, add elements to the heap. If the heap size exceeds $k$, remove the root (smallest). At the end, the root of the heap holds the $k$-th largest element."*
* **Complexity**: Time: $O(N \log K)$ | Space: $O(K)$
* **Java Solution**:
```java
public class KthLargestElement {
    public static int findKthLargest(int[] nums, int k) {
        // Natural ordering PriorityQueue = Min-Heap
        PriorityQueue<Integer> minHeap = new PriorityQueue<>(k);

        for (int num : nums) {
            minHeap.offer(num);
            if (minHeap.size() > k) {
                minHeap.poll(); // Evict the smallest element
            }
        }
        return minHeap.peek();
    }
}
```

### Problem 9: Number of Islands
* **Description**: Given an $m \times n$ 2D binary grid representing a map of `'1'`s (land) and `'0'`s (water), return the number of islands.
* **30-Second Interview Explanation**: *"Iterate over every cell in the matrix. When a `'1'` is found, increment our island count and trigger a DFS to visit and sink all adjacent connected lands by flipping `'1'`s to `'0'` (in-place) to avoid extra visited set memory."*
* **Complexity**: Time: $O(M \times N)$ | Space: $O(M \times N)$ for recursion stack
* **Java Solution**:
```java
public class NumberOfIslands {
    public static int numIslands(char[][] grid) {
        if (grid == null || grid.length == 0) return 0;
        int count = 0;

        for (int r = 0; r < grid.length; r++) {
            for (int c = 0; c < grid[0].length; c++) {
                if (grid[r][c] == '1') {
                    count++;
                    sinkIsland(grid, r, c);
                }
            }
        }
        return count;
    }

    private static void sinkIsland(char[][] grid, int r, int c) {
        // Boundary and water checks
        if (r < 0 || r >= grid.length || c < 0 || c >= grid[0].length || grid[r][c] == '0') {
            return;
        }

        // Mark cell as visited by sinking it to water
        grid[r][c] = '0';

        // Explore 4-directional neighbors
        sinkIsland(grid, r + 1, c);
        sinkIsland(grid, r - 1, c);
        sinkIsland(grid, r, c + 1);
        sinkIsland(grid, r, c - 1);
    }
}
```

### Problem 10: LRU Cache (Least Recently Used)
* **Description**: Design a data structure that follows the constraints of a Least Recently Used (LRU) cache with $O(1)$ `get` and `put` operations.
* **30-Second Interview Explanation**: *"Combine a HashMap with a Doubly Linked List with dummy head and tail nodes. The HashMap provides $O(1)$ key-to-node lookups. The Doubly Linked List tracks recency in $O(1)$: recently accessed nodes move to the head, and evictions drop the node right before the tail."*
* **Complexity**: Time: $O(1)$ for both `get` and `put` | Space: $O(\text{capacity})$
* **Java Solution**:
```java
public class LRUCache {
    private static class Node {
        int key, value;
        Node prev, next;
        Node(int key, int value) {
            this.key = key;
            this.value = value;
        }
    }

    private final int capacity;
    private final Map<Integer, Node> map;
    private final Node head, tail;

    public LRUCache(int capacity) {
        this.capacity = capacity;
        this.map = new HashMap<>();
        this.head = new Node(-1, -1);
        this.tail = new Node(-1, -1);
        head.next = tail;
        tail.prev = head;
    }

    public int get(int key) {
        if (!map.containsKey(key)) return -1;
        Node node = map.get(key);
        moveToHead(node);
        return node.value;
    }

    public void put(int key, int value) {
        if (map.containsKey(key)) {
            Node node = map.get(key);
            node.value = value;
            moveToHead(node);
        } else {
            if (map.size() >= capacity) {
                Node lru = tail.prev;
                removeNode(lru);
                map.remove(lru.key);
            }
            Node newNode = new Node(key, value);
            map.put(key, newNode);
            addToHead(newNode);
        }
    }

    private void addToHead(Node node) {
        node.next = head.next;
        node.prev = head;
        head.next.prev = node;
        head.next = node;
    }

    private void removeNode(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    private void moveToHead(Node node) {
        removeNode(node);
        addToHead(node);
    }
}
```

### Problem 11: Best Time to Buy and Sell Stock
* **Description**: Given an array `prices` where `prices[i]` is the price of a given stock on the $i$-th day, find the maximum profit you can achieve from a single buy and sell transaction in the future. If no profit can be achieved, return 0.
* **30-Second Interview Explanation**: *"Instead of comparing every pair in $O(N^2)$, make a single pass through the array. Track the minimum buy price seen so far (`minPrice`) and the maximum profit achieved (`maxProfit`). For each day, if the current price is lower than `minPrice`, update `minPrice`. Otherwise, evaluate if selling today yields a higher profit than `maxProfit`."*
* **Complexity**: Time: $O(N)$ | Space: $O(1)$
* **Java Solution**:
```java
public class BestTimeToBuyStock {
    public static int maxProfit(int[] prices) {
        if (prices == null || prices.length < 2) return 0;

        int minPrice = Integer.MAX_VALUE;
        int maxProfit = 0;

        for (int price : prices) {
            if (price < minPrice) {
                minPrice = price;
            } else if (price - minPrice > maxProfit) {
                maxProfit = price - minPrice;
            }
        }
        return maxProfit;
    }
}
```

### Problem 12: Search in Rotated Sorted Array
* **Description**: Given an integer array `nums` sorted in ascending order (with distinct values) that has been rotated at an unknown pivot, find the index of a given `target` in $O(\log N)$ runtime.
* **30-Second Interview Explanation**: *"Use a modified Binary Search. At any midpoint `mid`, at least one half of the array is guaranteed to be sorted. Check if the left half is sorted (`nums[low] <= nums[mid]`). If it is sorted, check if `target` falls within `[nums[low], nums[mid]]`. If yes, narrow search to the left; otherwise, go right. If the left half is not sorted, the right half must be sorted—apply the symmetric boundary check."*
* **Complexity**: Time: $O(\log N)$ | Space: $O(1)$
* **Java Solution**:
```java
public class SearchRotatedSortedArray {
    public static int search(int[] nums, int target) {
        if (nums == null || nums.length == 0) return -1;

        int low = 0;
        int high = nums.length - 1;

        while (low <= high) {
            int mid = low + (high - low) / 2;

            if (nums[mid] == target) return mid;

            // Check if left half is sorted
            if (nums[low] <= nums[mid]) {
                if (target >= nums[low] && target < nums[mid]) {
                    high = mid - 1; // Target lies in the sorted left half
                } else {
                    low = mid + 1;  // Target lies in the right half
                }
            } 
            // Otherwise, right half is guaranteed to be sorted
            else {
                if (target > nums[mid] && target <= nums[high]) {
                    low = mid + 1;  // Target lies in the sorted right half
                } else {
                    high = mid - 1; // Target lies in the left half
                }
            }
        }
        return -1;
    }
}
```
